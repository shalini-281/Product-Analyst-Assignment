# Part 1 — Data Quality & Governance Audit

**Section:** Pipeline & Modelling · **Status:** Complete

**The ask.** Data quality report as a table — `Issue | Evidence | Root cause | Fix | Prevention control` — covering the issues that would actually break a churn model or a governance audit.

## How to run

```bash
python Assignment_solution/part1/code/run_audit.py
```

~5 seconds. Rebuilds all 23 evidence tables in `output/` from the raw CSVs, which are
never modified. Every number quoted below is regenerated by that command.

## Method, and the one decision that shaped everything

**Every column is read as `VARCHAR`.**

```sql
CREATE OR REPLACE VIEW tx_raw AS
SELECT * FROM read_csv('transactions.csv', all_varchar = true, header = true);
```

If the CSV reader is allowed to sniff types, it silently coerces the malformed values
this audit exists to find: the 1,500 `MM/DD/YYYY` dates become `NULL`, and the report
then says *"1,500 nulls in transaction_date"* instead of *"a second date format is
present"*. Same count, completely different root cause, completely different fix. **The
reader would have destroyed the evidence before it could be measured.** So the parser is
explicit, ours, and fail-closed — anything it cannot read stays `NULL` and gets counted.

### Scope filter

An exhaustive list of every possible check is noise. A check earns a row in the report
only if it fails one of two lenses:

| Lens | Meaning |
|---|---|
| **MODEL** | corrupts the churn label, corrupts a feature, or changes a member's row count in a join |
| **GOVERNANCE** | exposes PII, breaks identity resolution, or blocks traceability |

13 findings survived that filter. Checks that came back clean are also kept (below), so
the audit doubles as a regression test rather than a one-off narrative.

## Assumptions

1. **Time anchor is `2026-06-30`** — the maximum transaction date in the file — not the
   wall clock. Recency and "future-dated" claims are relative to the data's own present,
   so the report reproduces identically on any future run.
2. **`transaction.brand` is where the purchase happened; `member.brand` is the enrolling
   brand.** They disagree for 9.3% of transactions. Treated as legitimate cross-brand
   shopping, *not* a defect — but it decides the join key for any brand-level analysis
   (this becomes decisive in Part 6).
3. **`amount > 10,000` is corrupt, not a whale.** p99 of legitimate amounts is ~286 and
   the maximum plausible basket is ~600, so the flagged rows are three orders of
   magnitude out. The threshold is not a judgement call about big spenders.
4. **Byte-identical rows are replays, not coincidence.** Two rows agreeing on member,
   timestamp *to the second*, amount to the cent, channel and brand are not two genuine
   purchases.
5. **The export is a full snapshot, not a delta.** Nothing in the files indicates
   incremental load boundaries.

## What the results actually say

**1. The most dangerous field in this dataset is the one that looks most useful.**
`status` presents as a ready-made churn label. It is decorative. Active, inactive and
churned members are separated by **0.7 percentage points** of 90-day activity and about
**5 days** of mean recency. A churn model trained on it learns noise and ships with
respectable-looking offline metrics — the worst possible failure mode, because nothing
breaks loudly. This single finding redirects Part 2's entire label design.

**2. Three loaders wrote this file, and the `transaction_id` prefix gives them away.**

| id family | rows | orphan members | implausible amounts | date range |
|---|---|---|---|---|
| `T#####` mainline | 191,308 | 0 | 0 | 2021-01-05 → 2026-06-30 |
| `TX#####` orphan source | 2,988 | **2,988 (100%)** | 0 | 2025-01-01 → 2026-06-29 |
| `TO####` corrupt batch | 15 | 0 | **15 (100%)** | **2026-02-15 only** |

Each family is perfectly homogeneous in its defect. That is what turns two vague
observations into two precise root causes: the `TX` family is not "some missing members"
but **an entire unloaded source system**, and the `TO` family is not "some bad values"
but **one bad load on one day**. Naming the date and the namespace is the difference
between an audit finding and a work ticket.

**3. Not everything that looks broken is broken — and the distinction changes the fix.**
Three findings inverted on inspection:

- The negative amounts look like refunds. They are **sign errors** — no clawback exists,
  points were computed on the magnitude, and not one of 1,995 has a paired original.
  Netting them as refunds would have corrupted every monetary feature.
- The slash dates look ambiguous. They are **provably `MM/DD/YYYY`** — component 1 never
  exceeds 12 while component 2 reaches 31.
- The null points look like data loss. They are **exactly recoverable**, because points
  are deterministic (`round(rate × amount)`, 100.0% within one point).

In each case the careless fix — net the refunds, guess `dayfirst`, drop the nulls —
produces a plausible table that is quietly wrong.

**4. The duplicate problem is two problems.** 1,995 duplicated ids decompose into
**1,936 replays** (byte-identical, safe to collapse) and **59 collisions** (same id,
genuinely different transactions). `DISTINCT` or `GROUP BY transaction_id` — the reflex
fix — silently deletes 59 real transactions. Different root causes, different fixes; they
must not be reported as one number.

**5. The governance findings are the ones that would fail an audit today.** Unmasked
email, name and birth date sit on local disk for all 50,160 members. And because 20
emails map to multiple `member_id`s, a DSAR keyed on `member_id` returns an *incomplete*
record — the request appears satisfied while personal data remains undisclosed.

**6. Earn rates differ by brand, and they are exact constants:**

| brand | earn rate | determinism (within 1 point) |
|---|---|---|
| PulseEats | **1.75** pts/$ | 99.9953% |
| PulseHome | **2.00** pts/$ | 100.0000% |
| PulseMart | **2.30** pts/$ | 100.0000% |

Not a defect, but the single most consequential fact in the file — it makes the corrupt
amounts and null points recoverable, and it settles Part 6.

## Deliberately excluded from the table

- **`transaction_type` has exactly one value (`purchase`).** Not a defect — but it means
  **redemptions are embedded in purchase rows rather than existing as their own events**.
  A member who redeemed without buying is invisible. This caps what any redemption
  feature can measure (Part 2) and is a material caveat for the liability figure (Part 8).
- **Transaction brand ≠ member brand for 9.3% of rows.** Cross-brand shopping, not an
  error. Recorded because it dictates the join key in Part 6.
- Cosmetic checks with no downstream effect (column ordering, trailing whitespace in
  names, file encoding) were run and omitted.
